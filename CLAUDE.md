# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A small Python harness for a fleet of Claude Code agents, built on one SQLite file, `agent.db`.

## Commands

Python 3.14 is required (`uuid.uuid7()`, and the unparenthesized `except A, B:` in `fleet/doctor.py`). Install the `iterum` command once with `uv tool install --editable .` (editable, so it runs this checkout's code); it works from any folder except where noted.

```bash
iterum status                                   # freeze, spend, receiver, runs, queue, what needs a person, canary; exit 1 when something needs a person
iterum report [--date D | --days N | --run RUN_ID | --serve [--port 8780]] [--out page.html] [--open] [--pdf] [--json]   # a day's work as one HTML page in reports/ beside the database, plus a page per linked run and an index.html (--pdf: also a PDF, via headless Chrome), or the data as JSON; a day with no activity writes nothing and says so
iterum doctor                                   # audit this machine, writes ./harness-audit.json
uv run scripts/seed-ledger.py                   # from the repo root: record ./harness-audit.json as layer.checked events
iterum project                                  # rebuild knowledge; exits 1 on DRIFT (first run always DRIFT)
iterum drill run                                # from the repo root: the six-step kill-and-resume drill
iterum run p.json                               # a plan: [[seq, intent, command, [resource, ...]], ...]; resources optional
iterum run p.json --allow-claude <usd>          # a plan with {"prompt": ...} steps: billed, each capped at <usd>
iterum run p.json --allow-claude <usd> --fix-retries N   # on a failed step after a prompt step, rerun the prompt step with the error, up to N times (each billed)
iterum resume <run_id> [--plan p.json] [--allow-claude <usd>] [--force]
iterum recovery [--idle-seconds 60] [--max-attempts 3]   # list dead runs, halt over-retried ones
iterum recovery halt <run_id> "<reason>"        # give up on one failed or stale run (logs run.halted)
iterum sync [export|import]                     # no argument: export, commit, pull, push, import, rebuild
iterum add "<cmd>" [--max-attempts 1] [--repo DIR --branch NAME [--base main]]   # queue a shell command (usually `iterum run <plan>`) for a worker; default one attempt; with --repo, the worker runs it on a new branch from --base and switches back after
iterum worker <name> [--budget-s 30]            # claim, run and report tasks until the budget ends
iterum dlq [redrive <task_id>]                  # list dead-lettered tasks, or put one back on the queue
iterum conflicts [resolve <task_id> "<decision>"]   # list conflicts waiting for a person, or settle one
iterum view [trace <run_id> | stages [days] | context [session]]   # live sessions and runs, one run's trace, failures per stage, or context size per request
iterum receiver [--port 4318]                   # receive Claude Code telemetry; settings in .env.example
iterum budget [set <usd>]                       # show the fleet's spend ceiling and headroom, or set the ceiling
iterum land <branch> --run-id R [--fence file:path=N ...] [--repo .] [--target main] [--check CMD]   # land a branch if every changed file has a live claim (and CMD passes on the merged tree); without --fence, the run's claims from the database
iterum approve|deny <fingerprint> [<who>]       # settle a pending approval (iterum status lists them); who defaults to ITERUM_DEVICE
iterum freeze [<who>] "<reason>"                # stop queue claims; iterum thaw [<who>] lifts it
iterum canary [--baseline-hours 24] [--window-hours 1] [--tolerance 0.5]   # flag recent runs whose median events, seconds or cost moved past tolerance
iterum eval [--json | add <name> <run_id> [--expect JSON]]   # replay every eval case (exit 1 if a regression case fails), print {case: passed}, or add one from a run
iterum scorecard <before> [<after>]             # eval cases at two git revisions (default after: the working tree); exit 1 if one broke
iterum sweep a.json b.json [...] [--repeats 5] [--base main] [--allow-claude <usd>]   # from the app repo: each plan N times in rotated order, pass rate beside cost
iterum drill merge|claims|kill                  # the merge gate (a few seconds), fleet.run's claims and a SIGKILLed worker (about 50s each)
```

`fleet/cli.py` maps each word to a module and runs it as `python -m` would, line-buffered in place of `-u`, so `uv run python -u -m fleet.<module> ...` from the repo root still works for every command. `fleet` has no `__init__.py` (a namespace package, built by `uv_build`), so its modules must run with `-m`: `python fleet/run.py` fails with `ModuleNotFoundError`. `doctor.py` imports nothing from `fleet` and runs as a script; `seed-ledger.py` adds the repo root to `sys.path` itself.

There is no test suite and no linter configured. Verify changes by running the commands against a throwaway database:

```bash
ITERUM_DB=/tmp/scratch.db ITERUM_DEVICE=test iterum drill run
```

## Settings

- `ITERUM_DEVICE`: required for anything that writes an event; `db.log()` raises without it.
- `ITERUM_CLAIM_TTL`: seconds a `fleet.run` claim lasts between renewals, default 300.
- `ITERUM_DB`: database path, default `$XDG_DATA_HOME/iterum/agent.db`, or `~/.local/share/iterum/agent.db` when `XDG_DATA_HOME` is unset (`db.default_path()`; `fleet/doctor.py` keeps a copy). `db.init()` creates the folder.
- `ITERUM_IDLE_SECONDS`: heartbeat age after which a `running` run counts as dead, default 60; the default for `fleet.recovery --idle-seconds` and for `--resume`.
- `ITERUM_MAX_ATTEMPTS`: the default for `fleet.recovery --max-attempts`, default 3.
- `ITERUM_SYNC_DIR`: sync folder, default `~/private-data/iterum`; must sit inside a git repo with a remote for `sync`.

## Architecture

`agent.db` keeps three contracts apart, and code must not blur them:

| Contract | Tables | Rule |
| --- | --- | --- |
| Control state | `runs`, `steps`, `receipts` (and the queue/claims/budget tables) | Mutable, local to one machine |
| Event ledger | `events` | Append-only; triggers abort any UPDATE or DELETE |
| Derived knowledge | `knowledge` | Rebuilt from events by `fleet/project.py`; never written directly |

`fleet/db.py` is the only database access layer:

- Every write goes through `db.write()`, which opens `BEGIN IMMEDIATE` (connections use `isolation_level=None`, so this explicit transaction is the only one).
- A state change and its `db.log()` event go in the same `db.write()` block, so they commit together.
- `db.log()` reserves `run_id`, `kind`, `stage` and `seq`; passing one as payload raises `TypeError` at call time. Rename the payload key instead.
- `db.init()` runs `schema.sql` and is safe to repeat; entry points that may meet a fresh database call it first.

`fleet/run.py` is write-ahead: each step is written `proposed` before its shell command runs and `committed` after; a failing command marks the step and run `failed` (`iterum run` then prints `run <id> failed: <error>` and exits 1), and `shell()`'s error keeps the last 2,000 characters of stdout and stderr, color codes removed (a Next.js type error is on stdout only). Resume skips the set of committed seqs (not `MAX(seq)+1`). The ledger stores intents and, in `step.proposed`, a `command_hash` (of the shell string or the whole prompt object), so `check_resumable()` compares the recorded intents to the plan by seq and refuses on mismatch, refuses a changed command unless that step is `failed` (a failed step's command may be fixed; runs logged before the hash existed are not checked), an unknown run, a run already `done`, or, without `--force`, a `halted` run or a `running` run whose heartbeat is younger than `recovery.IDLE_SECONDS` (`ITERUM_IDLE_SECONDS`, default 60), or a run with an uncommitted step whose command's process group (`steps.pgid`; each step runs in its own, killed by `_spawn()` on Ctrl-C or SIGTERM) is still alive. `fleet/run.py` refreshes `runs.heartbeat_at` from a thread every `HEARTBEAT` seconds; `fleet/recovery.py` reports `failed` runs and `running` runs whose heartbeat is older than `--idle-seconds` (default 60), and halts any whose most-proposed step has reached `--max-attempts` (proposals rerun by a `fix.retry` do not count). Every `fleet.run` start prints those stale `running` runs and a count of `failed` ones (`notice_dead_runs()`, read-only); nothing calls `fleet.recovery` itself. A plan step's optional fourth field lists resources (`"file:a.txt"`); a plan that declares any must run on a branch other than `--target` (default `main`); `claim_files()` claims them all, in sorted order, before any step runs and again on resume, the heartbeat thread renews them at half `ITERUM_CLAIM_TTL`, and a refused renewal kills the step and fails the run; the run prints the `iterum land` command with its fences when done. Before proposing each step it checks `governor.headroom()`: a shell step needs more than zero and a prompt step its whole cap, or the run is marked `budget_exhausted` and exits; a resume checks again.

A plan step's command is a shell string or `{"prompt": "...", "model": "..."}` (`model` optional, passed as `--model`; without it the user's default model). A prompt step runs `claude_step()`: `claude -p` in its own process group, billed to the user, so `check_prompt_steps()` refuses a plan with any prompt step unless `--allow-claude <usd>` is given, and refuses a prompt step that declares no files. The session gets `--max-turns 10`, `--max-budget-usd <usd>`, only the `Read,Edit,Write` tools with `acceptEdits` and `--permission-prompts none`, `--restricted` (file tools confined to the working directory; user and project settings ignored, `--settings` still applied), no MCP servers or tools (`--disallowedTools "mcp__*"`, `--strict-mcp-config`, and `ENABLE_CLAUDEAI_MCP_SERVERS=false` in `claude_env()`; `--tools` covers only built-in tools), no git status snapshot or CLAUDE.md files (`CLAUDE_CODE_DISABLE_GIT_INSTRUCTIONS=1`, `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1`), though the claude.ai account email still reaches it, `iterum.run_id` in `OTEL_RESOURCE_ATTRIBUTES`, and `fleet/gate.py` as a `PreToolUse` hook through `--settings` (`gate_settings()`, with `ITERUM_DB` and `FLEET_RUN_ID` in the hook's own command). It logs `claude.finished` (stage `tool_execution`: `exit_code` and the result envelope's `session_id`, `total_cost_usd`, `num_turns`, `is_error`, `permission_denials`, null when stdout is not JSON), then fails on a non-zero exit or `"is_error": true`, never on `subtype`. With `--fix-retries N` (default 0), a step that fails after a prompt step logs `step.failed` and `fix.retry` (`prompt_seq`, `attempt`, `error_tail`) and leaves the run `running`; the last prompt step before it runs again with the error's last `ERROR_TAIL` (2,000) characters appended (`with_feedback()`), then every step after it, each under the ceiling check; the recorded `command_hash` stays the plan's. Retries count per process, so a resume starts at 0; out of retries, the run fails as before. `fleet.replay` refuses runs with `fix.retry`. Resume refuses a prompt step that did not commit (`proposed` or `failed`) without `--force`, since it may have edited files and a rerun is billed again. One paid run (2026-11-11, `docs/claude-step-design.md` section 6) showed the hook runs in `-p` mode and refuses a claimed file; a session on 2026-11-12 showed the same under `--restricted`.

`fleet/sync.py` shares only `events` across devices: each device appends its own events to `events-<ITERUM_DEVICE>.jsonl` (export never removes lines) and imports every file with `ON CONFLICT(uid) DO NOTHING`. `uid` (UUIDv7) is the global identity; `event_id` is local and differs per device. `runs`, `steps` and the coordination tables are never synced.

`fleet/queue.py` is the work queue over `tasks` and `leases`. `claim()` issues a fence per task, and a worker must present it, with a live lease, to `heartbeat()`, `finish()`, `fail()` or `release_back()`; a stale worker gets `Fenced` or `Refused` and changes nothing. A dead-lettered task halts everything waiting on it, and `redrive()` restores those tasks. `fleet/worker.py` runs the loop and does the reaping itself, so there is no separate reaper process. The default `do_work` runs each command in its own process group, stored in `leases.pgid`; `reap()` leaves an expired lease alone while that group is alive (`fleet/proc.py`), and `_shell()` kills the group if it exits early. `fleet.run` and `fleet.worker` turn SIGTERM into `KeyboardInterrupt` (`proc.stop_on_sigterm()`), so a polite stop kills the command as Ctrl-C does; both then exit with -2, not -15. Ledger events use `task-<device>-<task_id>` as `run_id`, because `task_id` is local and events sync. `finish()` stores what `do_work` returns in `tasks.result`, read back with `queue.results()`. `claim()` skips tasks of kind `queue.HUMAN_KIND`; only `queue.resolve()` closes those. Before each claim, `fleet.worker` checks `governor.headroom()` and exits 1 at or below zero, leaving queued tasks queued; it never logs an event for this.

`fleet/merge.py` is the merge gate. `land()` builds the merge with `git merge-tree --write-tree`, then in one `db.write()` block calls `claim.require_claim()` for every changed file (or accepts the landing run's own expired claim whose row is unchanged, `claim.expired_own()`, listed under `expired` in `merge.landed`: a run is landed long after its claims stop being renewed) and moves the target with `git update-ref` and the expected old value; landing releases every claim it was given, in that block. A merge that would not change the target's files raises `Empty`. With `--check CMD`, `run_check()` runs CMD (it brings its own dependencies, e.g. `bun install --frozen-lockfile && bun run build`) in a temporary detached worktree of the merge commit, after `merge.started` and outside any transaction, and always removes that worktree; a non-zero exit logs `merge.refused` (`reason: "check failed"`, exit code, last 2,000 characters of output), keeps the claims and raises `CheckFailed`. The check runs before the claims check, so stale fences still pay for a full check. A SIGKILL mid-check leaves the worktree and the check's own process group behind (`docs/merge-check-design.md` section 6). It logs `merge.started` first; `reconcile()`, run by `main()` under an exclusive lock before `land()`, settles a merge a crash left without an outcome. The target branch must not be checked out in any working tree: `update-ref` leaves that tree's index behind.

`fleet/gate.py` is a `PreToolUse` hook that refuses (exit 2) an edit to a file another run has claimed, and exits 2 on any failure of its own, since any other exit code lets the edit through. It needs an absolute `ITERUM_DB` and a `FLEET_RUN_ID`, and runs as a script. Nothing in this repo registers it, deliberately: a checked-in `.claude/settings.json` would run it against anyone who clones the repo.

`fleet/telemetry.py` receives Claude Code's OTLP logs as `http/json` on `/v1/logs` and logs each `claude_code.api_request` as a `spend.reported` event, stage `governance`, under `iterum.run_id` (or `session-<session.id>`). It stores no identity fields and skips a `request_id` already logged. Metrics are not imported; `runs.cost_usd` is not written. `GET /v1/logs` answers `{"db": <resolved path>}`, the database it writes to.

`fleet/governor.py` is the fleet-wide spend ceiling. Spend is the sum of `cost_usd` over `spend.reported` events since the ceiling was first set (`budgets.window_start`); it keeps no counter, and `budgets.spent_usd` is unused. It counts only what `fleet.telemetry` received, and a run can pass the ceiling by up to one step's spend; nothing is reserved, so runs that check at the same moment each can (two concurrent runs passed it by two steps' spend, decision log 2026-11-12). So a plan with prompt steps under a ceiling refuses to start or resume (`check_receiver()` in `fleet/run.py`) unless `CLAUDE_CODE_ENABLE_TELEMETRY=1` and `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` are set (`source .env.example`) and the receiver answers with the run's own database; a receiver that dies mid-run is still missed.

`fleet/replay.py` rebuilds a `fleet.run` run's plan from its `step.proposed` events and drives the real `run.run_steps()` against a scratch database (`db.DB` swapped in `scratch_db()`), passing a `do_step` that plays back each step's recorded attempts: a committed result, a failed error (`RuntimeError`), or a kill (`KeyboardInterrupt`, for a step proposed with no outcome), resuming as often as the ledger shows. It returns the end state (`end`, `failed_stage`, `committed`); a step run more often than recorded makes `end` "diverged at step N". It calls no model and no shell, needs `ITERUM_DEVICE`, does not replay claims, the heartbeat or `check_resumable()`, and refuses runs with events it cannot reproduce (`fleet/step.py` runs, halts, budget stops, claim refusals). A queue task (`task-<device>-<id>`) is re-added with the kind and `max_attempts` from `task.added` (tasks logged before `task.added` carried `max_attempts` are refused), then claimed with the real `queue.claim()` and run with `worker._run_one(task, worker, work)` once per recorded claim, its `work` playing back the recorded `task.done` or `task.failed`, and redriven where the ledger shows `task.redriven`; `queue.time` is patched with a `Clock` that skips past each backoff, a claim the queue refuses makes `end` "diverged at claim N". A reaped claim runs no work: the clock moves past `queue.LEASE_TTL` and the real `worker._reap()` runs. A task with a dependency gets a chain of stand-in ancestors (`chain_depth()` walks the recorded `depends_on` values up to the task its halt reason names, else one), finished before its next claim; a recorded `task.halted` dead-letters the first ancestor and a `task.restored` redrives it, and `_expect()` makes `end` "diverged at halt" or "diverged at restore" if the real queue did not follow. `recorded_task()` reads the real ledger, so it runs before `scratch_db()`. Releases and deadline halts are refused. `fleet/eval.py` stores cases in `evals`: a regression case expects the end state its run actually reached; a capability case expects a hand-written one and never fails the suite. Results go to `eval_results`. `fleet/scorecard.py` runs `fleet.eval --json` for a revision in a temporary worktree (`merge.run_check()`), with `ITERUM_DB` made absolute, and the working tree in-process; it reports each case FIXED or BROKE. Revisions before `--json` existed cannot be scored.

`fleet/sweep.py` runs from the repo the plans work on, as `fleet.run` does. Each repeat rotates the plan order (a fixed order skews cost: the first request pays to write the prompt cache) and runs each plan as a `fleet.run` subprocess on a new branch `sweep/<time>/<plan>-<n>` from `--base`. Those branches are never landed, so after each run it releases the run's claims, and a later run can claim the same files at once. It refuses a dirty tree. A run that did not finish (a failed check step, say) stops before the plan's commit step, so `keep_leftovers()` commits what it left on that run's branch and the run counts as a fail; a run that finished and still left changes stops the sweep, cleaning nothing. The report gives pass count (`runs.status` = `done`) and mean, min and max cost (`spend.reported` per run) per plan, and for each pair either which cost less on every run or NO SIGNAL when the cost ranges overlap. A sweep stopped early prints no report. The empty branches stay in the app repo.

`fleet/approve.py` is the approval gate. `require(scope, seq, action, params)` returns for an action not in `IRREVERSIBLE` (exact names) or already approved, and otherwise records a `pending` row and raises `NeedsApproval` (or `Denied`); `scope` names the work, not the run, and the fingerprint hashes it with seq, action and params, so a changed parameter asks again and a restart does not. `decide()` settles only a pending row. Nothing calls `require()` yet. `freeze()` inserts a `FROZEN` row in `budgets`, and `queue.claim()` returns `None` while it exists; `fleet.run` does not check it, and `budgets` does not sync.

`fleet/canary.py` compares finished `fleet.run` runs in the last window with those before it (median events, seconds, and cost from `spend.reported` events; `runs.cost_usd` is never filled) and logs `canary.fired` when one moves by more than the tolerance. It detects change, not wrong output, needs 5 baseline runs, and skips a measure whose baseline median is zero.
