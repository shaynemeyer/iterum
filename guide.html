User guide

Running a fleet of Claude Code agents with Iterum

Iterum runs plans: numbered steps of shell commands and Claude Code prompts. It records every step in agent.db before running it, so a run can be killed and resumed, and it claims the files each step touches, so parallel agents cannot land over each other. This guide takes you from a first free run to shipping a feature written by a model, landed through a build check.

Free

Shell steps

Run any command. Nothing is billed. Every drill and dry run in this guide is free.

Billed

Prompt steps

Run claude -p on your account. Each is capped, and nothing runs without --allow-claude.

Rule of thumb

Plans from the app repo

Install iterum once. Run plans and landings from the repo they work on; everything else runs from any folder.

A typical session

  1. Plan it with /iterum:fleet-plan from a Claude Code session in the app repo: one sentence about the feature. It asks until nothing is open, then writes the plan, a check script and a plan document, proves the check fails on main, and dry-runs the plan for free. Planning a feature.

  2. Read the plan document: the files, the prompt, what the check looks for, the model and the cap. Nothing is billed until you say yes. To write plans yourself, see Writing plans by hand.

  3. Run it now, or queue it for the night. Now: start the receiver, load the telemetry settings, and run it with --allow-claude and --fix-retries 2 on a feature branch. Tonight: queue it with iterum add and start a worker. A night's queue.

  4. Land it with the printed command plus --check. If it is refused, fix on the branch and land again. Landing a branch.

  5. If anything stops, read its status and resume; nothing finished runs twice. When a run stops. Delete the merged branch when you are done.

Where to run what

Install iterum once (Before you start) and its commands run from any folder against one database, ~/.local/share/iterum/agent.db. Where you start still matters for two kinds of command: those that change your app run from the app repo, because steps run in the folder you start from and the merge gate lands the branch there; two harness commands need the Iterum repo.

A feature session therefore uses two terminals: the telemetry receiver, and the plan and the landing in the app repo (Shipping a feature).

Chapter 01

Before you start

You need Python 3.14 (Iterum uses uuid.uuid7()) and uv. Prompt steps also need the claude CLI, signed in.

Every event records which machine wrote it, so name this machine once, in your shell profile:

# ~/.zshrc or ~/.bashrc, then open a new terminal
export ITERUM_DEVICE=laptop

Then install the iterum command, audit the machine, and record the audit as the first events in the ledger:

git clone https://github.com/shaynemeyer/iterum.git && cd iterum
uv tool install --editable .      # installs iterum; editable, so a git pull updates it
iterum doctor                     # writes ./harness-audit.json
uv run scripts/seed-ledger.py     # records it as layer.checked events
iterum project                    # builds knowledge; the first run always reports DRIFT

To plan features from a sentence, install the iterum Claude Code plugin from your clone. It adds /iterum:fleet-plan to every project:

claude plugin marketplace add "$PWD"   # from the iterum clone: its .claude-plugin/marketplace.json
claude plugin install iterum@iterum
claude plugin list                     # iterum@iterum ... enabled
Cloned somewhere other than ~/github/iterum? Set ITERUM_HOME to the clone in your shell profile. /iterum:fleet-plan writes plans to $ITERUM_HOME/plans/, which git ignores, so your app's tree stays clean.
Shell cannot find iterum? Run uv tool update-shell and open a new terminal. Each iterum command runs a module as python -m would, so uv run python -m fleet.<module> from the Iterum repo still works. The database is created on first use at ~/.local/share/iterum/agent.db.
Chapter 02

Your first run: kill it, then resume it

iterum drill run runs a built-in six-step plan made of shell commands, from the Iterum repo. Step 5 sleeps for 20 seconds so you have time to kill it. Use a throwaway database while you learn:

  1. Start the drill against a scratch database.

    export ITERUM_DB=/tmp/scratch.db
iterum drill run

  2. When step 5 starts, press Ctrl-C (or close the terminal). Steps 1 to 4 are already committed; step 5 is left proposed, with no outcome.

  3. Resume it with the run id it printed. Resume waits until the run's heartbeat is 60 seconds old, so a live run is never resumed by mistake. Add --force only if you know the old process is gone.

    iterum resume <run_id>

    It skips steps 1 to 4, reruns step 5, and finishes with run <run_id> done.

Chapter 03

Planning a feature

A plan is a short list of numbered steps: usually a Claude Code prompt that makes the change, the build, a check that the change is there, and a commit. You do not have to write one: /iterum:fleet-plan writes it from one sentence and proves it before anything is billed.

Planning with /iterum:fleet-plan

Start Claude Code in the app repo and describe the feature in one sentence. The skill reads the repo and what past runs cost, then asks questions until nothing about the feature is open: what it does, which files, what counts as done, the model, the cap. A vague request gets questions, never a plan. Then it writes four files to $ITERUM_HOME/plans/<slug>/, proves the check fails on main, dry-runs the plan on a scratch database, and asks "Implement this feature?" Nothing is billed before your yes.

# in a Claude Code session started in the app repo
/iterum:fleet-plan add links back to the home page and to /notes on the not-found page
FileWhat it holds
plan.mdThe plan in plain words: feature, files, prompt, build, what the check looks for, model, cap, retries, chunks, and a last line Open questions: None.
plan.jsonPrompt step, build, check, commit; every step claims the same files.
dry.jsonThe same plan with the prompt replaced by echo dry, for the free run.
check.shRuns after the build. Prints every miss, one line each, on stderr, and exits 1 if there was any. Each line names exactly what is expected, because it becomes the model's feedback on a retry.
One task per file per night. A feature larger than one prompt step is split into chunks of one to three files. Chunks that share a file, or depend on each other, go into one plan as steps in order; only chunks with no file in common become separate plans. A run keeps its claims until it is landed, so a second plan on the same file would be refused.
Prefer to write plans yourself? Writing plans by hand covers the plan format, the rules every plan follows, prompt steps, check scripts and the free proofs, step by step.
Chapter 04

Prompt steps: letting Claude write the change

A prompt step runs one Claude Code session, billed to you, only with --allow-claude and a dollar cap. /iterum:fleet-plan writes the prompt; this is what the session it starts may do.

It can

Read, Edit and Write

Only those three tools, only inside the working directory (--restricted). Edits need no approval.

It cannot

Run commands

No shell, no MCP servers, no web. Put the build and your checks in shell steps after it.

It does not see

Your project instructions

No CLAUDE.md or AGENTS.md, and no git status. Put everything it needs in the prompt.

It is stopped by

Claims

The gate hook refuses an edit to a file another run has claimed, and tells the model why.

A prompt step that did not commit needs --force to resume. It may already have edited files, and running it again is a second billed session. Check git status and git diff on the branch first.
Chapter 05

Running and landing it

Once the plan is written and proven, the rest is: start the receiver, run it, land it. The first three stages below are free, and /iterum:fleet-plan has already done the first two.

The paid run and the landing, from the app's repo
# terminal 1, anywhere: the receiver, on the same database the run uses
iterum receiver

# terminal 2, from the app repo, on a feature branch
source <iterum>/.env.example
git switch -c feat/note-footer main
iterum run <iterum>/plans/note-footer/plan.json --allow-claude 0.05 --fix-retries 2
run 663ba8f2873c started
  step 1  notes footer  -> committed
  step 2  build  -> committed
  step 3  check the footer  -> failed; fix retry 1/2 from step 1
  step 1  notes footer  -> committed
  step 2  build  -> committed
  step 3  check the footer  -> failed; fix retry 2/2 from step 1
  step 1  notes footer  -> committed
  step 2  build  -> committed
  step 3  check the footer  -> committed
  step 4  commit it  -> committed
run 663ba8f2873c done
land with: iterum land feat/note-footer --run-id 663ba8f2873c --fence 'file:app/notes/[slug]/page.tsx=16'

iterum land feat/note-footer --run-id 663ba8f2873c \
  --check "bun install --frozen-lockfile && bun run build"   # add --check yourself: it runs in a fresh copy, so install first

The fix loop

With --fix-retries N, a step that fails after a prompt step does not end the run. Its error, the last 2,000 characters, is added to the prompt, and the prompt step runs again, then every step after it, up to N times, each under its own cap. In the run above, the check named a missing sentence; the retry added it, and the check then named a missing link; the second retry added that and passed. Out of retries, the run fails as before.

What it costs. Across 54 Haiku prompt steps so far, the median cost was $0.0011 and 43 cost under $0.003; the most was $0.023, in 2 to 13 turns. The run above cost $0.00277 for three tries. The cap is Claude Code's own estimate, which spend can pass, so a step's real limit is close to its cap, not exact.
Chapter 06

Landing a branch

A finished run prints its land with: command, with one --fence per claimed file. Paste it as printed: fences with shell characters, like [slug], are already quoted. Add --check to build the merged tree before it lands.

iterum land builds the merge without touching your working tree, runs the check in a temporary worktree, then, in one transaction, requires a live claim at the given fence for every changed file and moves the target branch only if it has not moved since. Landing releases the claims.

It saysWhat happenedWhat to do
landed <branch> on mainMerged; claims released.Delete the branch when you like (git branch -d).
merge.refused, check failedThe merged tree failed your check, often two branches that each built alone. main is unchanged; the claims are kept.Fix it on the branch, commit, and run the same land command again while the claims are live.
a fence refused as stale, or a claim released or expiredToo much time passed, or another run took the file.Rerun the plan's edits on a new run, which claims again.
EmptyThe branch would not change any file on the target.Nothing to land.
Do not have the target branch checked out anywhere when you land. update-ref moves the branch, and a checkout of it would be left with a stale index.
Chapter 07

When a run stops

Every iterum run start lists runs that look dead and counts failed ones. iterum recovery gives the full list and halts any run whose same step has been tried too often. Find the run's status, then follow its path:

iterum status                                 # exit 1 when a run is stale or failed
iterum recovery                               # list dead runs; halt over-retried ones
iterum recovery --idle-seconds 120 --max-attempts 5
iterum recovery halt <run_id> "superseded"     # give up on one; it leaves iterum status
iterum view trace <run_id>                    # the run stage by stage, failing stage named

Resume also refuses when it would be unsafe: a step's process is still alive, the plan's intents differ from the recorded ones, or a non-failed step's command changed. Each refusal prints the exact command to run once you have checked.

Chapter 08

Controlling spend

Set a ceiling for the whole fleet. Spend is counted from what Claude Code itself reports, so the telemetry receiver must be running.

iterum budget set 3        # a $3.00 ceiling; spend counts from the first time you set one
iterum budget              # show it
ceiling 3.00  spent 2.3859  headroom 0.6141 USD  (since 2026-11-11 10:44)
iterum budget reset        # count from zero again, keeping the ceiling
reset: 2.3859 USD no longer counted
ceiling 3.00  spent 0.0000  headroom 3.0000 USD  (since 2026-11-14 07:30)

A budget for the night. Setting a ceiling changes only the limit; spend keeps counting from the first time you set one. Before a night's queue, set the ceiling to what you will spend tonight and reset, and in the morning iterum budget shows what the night cost. The reset is logged as a budget.reset event with the spend it set aside, so nothing is lost from the ledger.

iterum budget set 1
iterum budget reset
Your own sessions count too. The receiver records any Claude Code session started from a shell where .env.example was sourced, and the ceiling adds up everything it records. Source it only in the terminal that runs plans and workers, and start your interactive claude elsewhere.

Turning on telemetry

A plan with prompt steps under a ceiling refuses to start unless telemetry is on and the receiver answers with the run's own database. Start the receiver, then load the settings in the shell that runs the plan:

iterum receiver                              # listens on 127.0.0.1:4318
curl -s localhost:4318/v1/logs               # answers {"db": "/abs/path/agent.db"}
source <iterum>/.env.example                 # CLAUDE_CODE_ENABLE_TELEMETRY=1 and the endpoint
iterum status                                # RECEIVER: up, writing to this database
The ceiling is soft. A run can pass it by up to one step's spend, and runs that check at the same moment each can. Spend the receiver never received (because it was down) is not counted.
Chapter 09

Running work in parallel

Give each run its own working tree and branch, and point every run at the same database and receiver. Claims keep them from editing the same file; the merge gate keeps them from landing over each other.

git worktree add -b feat/latest ../app-latest main
cd ../app-latest && bun install --frozen-lockfile        # each tree needs its own dependencies
# then start each run from its own tree, at the same time
git worktree remove ../app-latest                           # when done; refuses if it has changes
Starting runs together on a brand-new database? Run any iterum command, such as iterum budget, once first. Current code waits out the startup race, and initializing first avoids it altogether.
Chapter 10

The work queue

The queue holds work for later: shell commands, usually whole plans. iterum add queues one; workers claim them under a 30-second lease with a fence, run them, and report one outcome. A task gets one attempt unless you say otherwise, because a plan already retries inside itself (--fix-retries) and rerunning it whole cannot help.

iterum add "echo hello"
task 1 queued
iterum add "make test" --max-attempts 3      # retried after a backoff: 5 s, then 10 s
iterum worker worker-1 --budget-s 5

A task that must wait for another needs depends_on, which only Python has today (from the Iterum repo):

uv run python -c "from fleet import db, queue; db.init();
a = queue.add('shell', {'cmd': 'echo hello'})
b = queue.add('shell', {'cmd': 'echo world'}, depends_on=a)
print(a, b)"
iterum worker worker-1 --budget-s 5
worker-1  task 1 (shell)  done
worker-1  task 2 (shell)  done
uv run python -c "from fleet import queue; print(queue.results([1, 2]))"
['hello', 'world']
iterum dlq                                  # dead-lettered tasks
iterum dlq redrive <task_id>                # put one back, with what waits on it
iterum conflicts                            # tasks waiting for a person
iterum conflicts resolve <task_id> "keep the newer schema"
FLEET_WORK_MODULE=mypackage.mywork iterum worker worker-1   # your own do_work(task), from its project folder

Freezing the queue. When output looks wrong, stop new work before you investigate. A frozen queue hands out no tasks; workers finish the ones they hold. The freeze is per machine, and it does not stop iterum run.

iterum freeze "output looks wrong since 03:00"   # recorded as by ITERUM_DEVICE
iterum status                                    # FROZEN or not, and pending approvals
iterum thaw                                      # last, after the fix is queued
Approvals. iterum status lists approval requests and iterum approve|deny <fingerprint> settles one. Requests come from approve.require(), which nothing in Iterum calls yet, so the list stays empty until your own code calls it.

A night's queue

Plan each feature with /iterum:fleet-plan and answer no to "Implement this feature?". Queue each plan with the app repo and a branch name, set the night's budget, and start one worker. For each task, the worker makes the branch from --base (default main), runs the plan there, and returns to the base detached, so iterum land can move it in the morning.

# terminal 1
iterum receiver

# terminal 2, the only one with the telemetry settings
source <iterum>/.env.example
iterum add "iterum run <iterum>/plans/not-found-links/plan.json --allow-claude 0.05 --fix-retries 2" \
  --repo ~/code/my-app --branch night/not-found-links
iterum add "iterum run <iterum>/plans/robots-sitemap/plan.json --allow-claude 0.05 --fix-retries 2" \
  --repo ~/code/my-app --branch night/robots-sitemap
iterum budget set 1 && iterum budget reset
iterum worker night-1 --budget-s 600
WhenThe worker
The plan finishesReturns the app to the base, detached: iterum land refuses a target that is checked out. The branch holds the plan's commit, ready to land.
The plan failsCommits whatever the failed run left on the task's own branch ("iterum: what task N left behind"), returns to the base detached, deletes the branch if it holds no commits (so the task can be queued again on the same name), and dead-letters the task with the end of the error: usually the check's own message.
The app has uncommitted changes before a taskHands the task back and stops, listing the changes. Every queued task stays queued. Nothing is cleaned up for you: the changes may be someone's work.
The ceiling is reachedStops before its next claim, leaving queued tasks queued.
A ceiling is set, but its shell has no telemetry settings or the receiver is not answeringStops before its next claim, leaving queued tasks queued: the ceiling could not count the night's spend. Start it from the shell where .env.example is sourced. It stops even for tasks with no prompt steps, since a task holds only a shell command.

Each run records its task (queue_task in its run.started event), so a run and the task that started it can be matched in the ledger. In the morning, iterum status, iterum dlq and iterum report show what finished and what failed; land each finished branch with iterum land and --check. Landing stays a decision for a person.

Use night/<slug>, not feat/<slug>. /iterum:fleet-plan's dry run already made feat/<slug>, and the worker cannot make a branch that exists. The empty feat/<slug> branches can be deleted.
Chapter 11

Seeing what happened

Every view is read-only except iterum canary, which logs a canary.fired event when it fires. The live-session half needs the claude CLI; without it you still get everything from the ledger.

CommandShows
iterum statusOne screen: freeze, spend, receiver, runs, queue, what needs a person, canary; exit 1 when something needs a person
iterum viewLive Claude Code sessions, then runs per agent from the ledger
iterum view trace <run_id>One run, stage by stage, with the failing stage named
iterum view stages [days]Failures per stage, default the last 7 days
iterum view context [session]Context size per session, or per request in one session
iterum budgetCeiling, spend and headroom
iterum recoveryFailed runs and running runs whose heartbeat went stale
iterum canaryRecent runs that look unlike the day before
sqlite3 ~/.local/share/iterum/agent.db "select kind, payload from events where run_id='<id>'"The raw ledger for one run, including claude.finished (cost, turns, denials)
What the canary compares. Median events, seconds and cost per run for finished iterum run runs in the last hour, against the 24 hours before; it fires past a 50% change (--tolerance). It needs 5 earlier runs, and cost needs iterum receiver. It flags change, not wrong output: a fleet that got cheaper and faster overnight is worth a look.
Chapter 12

Reports

iterum report writes a self-contained HTML page into reports/ beside the database (~/.local/share/iterum/reports/) and prints its path. A page opens offline: no network requests, one small inline script for sorting tables and chart tooltips, and it reads the same with scripts off. It starts with a banner saying whether anything needs a person.

iterum report --open                    # today, with 7-day trends
iterum report --date 2026-11-12 --pdf   # another day, and a PDF of it
iterum report --days 7                  # the last 7 days
iterum report --run <run_id>            # one run, step by step
iterum report --json                    # the same data, for scripts
iterum report --serve                   # live, on 127.0.0.1:8780

A day or several-day report also writes a page for each run it lists and rebuilds index.html, so run ids are links and every page links back to the index. A day with no activity writes nothing and says which dates have data. --serve answers only on 127.0.0.1, refuses requests for any other host name, and stops with Ctrl-C.

Chapter 13

Syncing devices

Only the event ledger moves between machines. Each device writes its own events-<device>.jsonl in a sync folder that sits in a private git repo with a remote, and imports every device's file, skipping events it already has. Runs, steps, claims and the queue stay on the machine that owns them.

export ITERUM_SYNC_DIR=~/private-data/iterum      # the default; must be inside a git repo with a remote
iterum sync           # export, commit, pull, push, import, rebuild knowledge
iterum sync export    # only write this device's events
iterum sync import    # only merge every device's events
Keep files from retired devices. They are the only shared copy of those events. Importing the same file twice changes nothing.
Chapter 14

Testing changes to Iterum

There is no unit test suite. Changes are checked with drills that crash the harness on purpose, and with recorded runs replayed through the real code. Run them against a scratch database.

CommandChecksTimeCost
iterum drill mergeMerge gate refusals, the lock, a crash mid-mergesecondsfree
iterum drill claimsClaim refusal, resume, renewal, takeover of a paused agentabout 50 sfree
iterum drill killSIGKILL a worker mid-task and check recoveryabout 50 sfree
iterum drill run (from the Iterum repo)The six-step write-ahead drillabout 25 sfree
iterum evalReplays every stored case; exit 1 if a regression case failssecondsfree
iterum scorecard <before> [<after>]Eval cases at two git revisions; FIXED or BROKE per casesecondsfree
iterum sweep a.json b.json --repeats 5Plans run N times in rotated order; pass rate beside costminutesbilled
 
export ITERUM_DB=/tmp/scratch.db ITERUM_DEVICE=test
iterum drill merge
iterum drill claims & iterum drill kill & wait
iterum eval add resume-case <run_id>    # keep a real run as a regression case
iterum scorecard main                   # did my working tree break any case?
When you add a check to a drill, break the code once to watch it fail, then undo the break by reversing your edit, not with git checkout, which also throws away uncommitted work.
