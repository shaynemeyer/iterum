User guide

Running a fleet of Claude Code agents with Iterum

Iterum runs plans: numbered steps of shell commands and Claude Code prompts. It records every step in agent.db before running it, so a run can be killed and resumed, and it claims the files each step touches, so parallel agents cannot land over each other. This guide takes you from a first free run to shipping a feature written by a model, landed through a build check.

Free

Shell steps

Run any command. Nothing is billed. Every drill and dry run in this guide is free.

Billed

Prompt steps

Run claude -p on your account. Each is capped, and nothing runs without --allow-claude.

Rule of thumb

Always from a repo

Run every command through uv, from the repo the plan works on, with -m for fleet modules.

A typical session

  1. Pick one small feature and the two or three files it touches. Create a branch for it in the app repo.

  2. Write the plan and a check script: prompt step, build, check, commit, every step claiming those files. Run the check on main and make sure it fails. Writing a plan, Prompt steps.

  3. Dry-run it for free on a scratch database with the prompt replaced by echo dry. It should fail at the check and nowhere else. Shipping a feature.

  4. Start the receiver, load the telemetry settings, run it for real with --allow-claude. Read the diff and the cost.

  5. Land it with the printed command plus --check. If it is refused, fix on the branch and land again. Landing a branch.

  6. If anything stops, read its status and resume; nothing finished runs twice. When a run stops. Delete the merged branch when you are done.

Where to run what

Work happens in two folders. Commands that change your app run from the app repo, because steps run in the folder you start from and the merge gate lands the branch there. Everything about the harness itself runs from the Iterum repo. Both must use the same database.

Run fromCommandsWhy there

fleet.sweep		Steps run in the current folder; the branch check and the landing use this repo.

source <iterum>/.env.example             # telemetry, for prompt steps under a ceiling
uv run --project <iterum> python -u -m fleet.run --plan feature.json

A feature session therefore uses two terminals: the telemetry receiver in the Iterum repo, and the plan and the landing in the app repo (Shipping a feature).

Chapter 01

Before you start

You need Python 3.14 (Iterum uses uuid.uuid7()) and uv. Prompt steps also need the claude CLI, signed in. There is no install step: uv builds the environment on the first run.

Every event records which machine wrote it, so name this machine once, in your shell profile:

# ~/.zshrc or ~/.bashrc, then open a new terminal
export ITERUM_DEVICE=laptop

Then audit the machine and record the audit as the first events in the ledger:

uv run fleet/doctor.py            # writes ./harness-audit.json
uv run scripts/seed-ledger.py     # records it as layer.checked events
uv run python -m fleet.project    # builds knowledge; the first run always reports DRIFT
Why -m? fleet is a namespace package with no __init__.py, so python fleet/run.py fails with ModuleNotFoundError. Use uv run python -m fleet.run. Only doctor.py and gate.py run as scripts.
Chapter 02

Your first run: kill it, then resume it

With no plan, fleet.run runs a built-in six-step drill made of shell commands. Step 5 sleeps for 20 seconds so you have time to kill it. Use a throwaway database while you learn:

  1. Start the drill against a scratch database.

    export ITERUM_DB=/tmp/scratch.db
uv run python -u -m fleet.run

  2. When step 5 starts, press Ctrl-C (or close the terminal). Steps 1 to 4 are already committed; step 5 is left proposed, with no outcome.

  3. Resume it with the run id it printed. Resume waits until the run's heartbeat is 60 seconds old, so a live run is never resumed by mistake. Add --force only if you know the old process is gone.

    uv run python -u -m fleet.run --resume <run_id>

    It skips steps 1 to 4, reruns step 5, and finishes with run <run_id> done.

Chapter 03

Writing a plan

A plan is a JSON list of steps. Each step has a number, a short intent, a command, and, optionally, the files it may touch.

feature.json, kept anywhere; run it from the app repo
[[1, "edit the page", "sed -i '' 's/Hello/Welcome/' app/page.tsx", ["file:app/page.tsx"]],
 [2, "build",         "bun run build",                              ["file:app/page.tsx"]],
 [3, "commit it",     "git add app/page.tsx && git commit -m 'Welcome'", ["file:app/page.tsx"]]]
From the app repo, with the settings from Where to run what
git switch -c feat/welcome                     # a plan that declares files must not run on main
uv run --project <iterum> python -u -m fleet.run --plan feature.json

Rules that keep plans safe

  • Declare files and you need a branch. A plan with resources refuses to run on --target (default main), because its commits would skip the merge gate.
  • All files are claimed before step 1, in sorted order, and renewed by a heartbeat at half ITERUM_CLAIM_TTL (default 300 s). If another run holds one, the run is refused before anything runs, and the message names that run.
  • A failing command fails the run. Fix the command for that step in the plan file and resume; committed steps stay committed.
  • Run from the repo the plan works on. Steps run in the directory you start from. From outside the Iterum repo, add PYTHONPATH=<iterum> and uv run --project <iterum>, and keep ITERUM_DB an absolute path.
Chapter 04

Prompt steps: letting Claude write the change

Replace a step's command with a prompt object and that step runs a Claude Code session. model is optional; without it, your default model is used.

[[1, "404 page", {"prompt": "Create app/not-found.tsx ... Create no other file.", "model": "claude-haiku-5-5"}, ["file:app/not-found.tsx"]],
 [2, "build",    "bun run build",                                                                      ["file:app/not-found.tsx"]],
 [3, "commit",   "git add app/not-found.tsx && git commit -m 'Add a 404 page'",                       ["file:app/not-found.tsx"]]]
uv run python -u -m fleet.run --plan feature.json --allow-claude 0.05   # each prompt step capped at $0.05
It can

Read, Edit and Write

Only those three tools, only inside the working directory (--restricted). Edits need no approval.

It cannot

Run commands

No shell, no MCP servers, no web. Put the build and your checks in shell steps after it.

It does not see

Your project instructions

No CLAUDE.md or AGENTS.md, and no git status. Put everything it needs in the prompt.

It is stopped by

Claims

The gate hook refuses an edit to a file another run has claimed, and tells the model why.

Writing prompts that work

  • Name the exact files to edit and say "change nothing else". Every prompt step must declare at least one file.
  • Say exactly what should appear, so a shell step can check it (see the next chapter).
  • If the task touches an API you know has changed, name the doc file that states the rule. A general "read the docs" hint cost about 7 times as much per run in testing.
A prompt step that did not commit needs --force to resume. It may already have edited files, and running it again is a second billed session. Check git status and git diff on the branch first.
Chapter 05

Shipping a feature, start to finish

This is the routine that shipped every feature run so far. The first three stages are free and catch most mistakes in the plan itself before any money is spent.

The paid run and the landing, from the app's repo
# terminal 1, from the Iterum repo: the receiver, on the same database the run uses
ITERUM_DB=<iterum>/agent.db uv run python -u -m fleet.telemetry

# terminal 2, from the app repo, on a feature branch
source <iterum>/.env.example
export ITERUM_DB=<iterum>/agent.db PYTHONPATH=<iterum>
uv run --project <iterum> python -u -m fleet.run --plan feature.json --allow-claude 0.05
run 12c0572d5ec1 done
land with: uv run python -m fleet.merge feat/home-copy --run-id 12c0572d5ec1 --fence file:app/page.tsx=5

uv run --project <iterum> python -m fleet.merge feat/home-copy --run-id 12c0572d5ec1 \
  --fence file:app/page.tsx=5 --check "bun install --frozen-lockfile && bun run build"
What it costs. Six Haiku feature steps on 2026-11-12 cost between $0.0011 and $0.0020 each, 3 to 5 turns, against a $0.05 cap.
Chapter 06

Landing a branch

A finished run prints its land with: command, with one --fence per claimed file. Paste it as printed: fences with shell characters, like [slug], are already quoted. Add --check to build the merged tree before it lands.

fleet.merge builds the merge without touching your working tree, runs the check in a temporary worktree, then, in one transaction, requires a live claim at the given fence for every changed file and moves the target branch only if it has not moved since. Landing releases the claims.

It saysWhat happenedWhat to do
landed <branch> on mainMerged; claims released.Delete the branch when you like (git branch -d).
merge.refused, check failedThe merged tree failed your check, often two branches that each built alone. main is unchanged; the claims are kept.Fix it on the branch, commit, and run the same land command again while the claims are live.
a fence refused as stale, or a claim released or expiredToo much time passed, or another run took the file.Rerun the plan's edits on a new run, which claims again.
EmptyThe branch would not change any file on the target.Nothing to land.
Do not have the target branch checked out anywhere when you land. update-ref moves the branch, and a checkout of it would be left with a stale index.
Chapter 07

When a run stops

Every fleet.run start lists runs that look dead and counts failed ones. fleet.recovery gives the full list and halts any run whose same step has been tried too often. Find the run's status, then follow its path:

uv run python -m fleet.recovery                       # list dead runs; halt over-retried ones
uv run python -m fleet.recovery --idle-seconds 120 --max-attempts 5
uv run python -m fleet.view trace <run_id>            # the run stage by stage, failing stage named

Resume also refuses when it would be unsafe: a step's process is still alive, the plan's intents differ from the recorded ones, or a non-failed step's command changed. Each refusal prints the exact command to run once you have checked.

Chapter 08

Controlling spend

Set a ceiling for the whole fleet. Spend is counted from what Claude Code itself reports, so the telemetry receiver must be running.

uv run python -m fleet.governor set 3        # a $3.00 ceiling; spend counts from the first time you set one
uv run python -m fleet.governor              # show it
ceiling 3.00  spent 2.3859  headroom 0.6141 USD  (since 2026-11-11 10:44)

Turning on telemetry

A plan with prompt steps under a ceiling refuses to start unless telemetry is on and the receiver answers with the run's own database. Start the receiver, then load the settings in the shell that runs the plan:

ITERUM_DB=$PWD/agent.db uv run python -u -m fleet.telemetry      # listens on 127.0.0.1:4318
curl -s localhost:4318/v1/logs                                  # answers {"db": "/abs/path/agent.db"}
source .env.example                                             # CLAUDE_CODE_ENABLE_TELEMETRY=1 and the endpoint
The ceiling is soft. A run can pass it by up to one step's spend, and runs that check at the same moment each can. Spend the receiver never received (because it was down) is not counted.
Chapter 09

Running work in parallel

Give each run its own working tree and branch, and point every run at the same database and receiver. Claims keep them from editing the same file; the merge gate keeps them from landing over each other.

git worktree add -b feat/latest ../app-latest main
cd ../app-latest && bun install --frozen-lockfile        # each tree needs its own dependencies
# then start each run from its own tree, same ITERUM_DB, at the same time
git worktree remove ../app-latest                           # when done; refuses if it has changes
Starting runs together on a brand-new database? Run uv run python -c "from fleet import db; db.init()" once first. Current code waits out the startup race, and initializing first avoids it altogether.
Chapter 10

The work queue

For many small independent jobs, use the queue instead of plans. Tasks are added from Python; workers claim them under a 30-second lease with a fence, run them, and report one outcome. The default worker runs the shell command in the task's cmd.

uv run python -c "from fleet import db, queue; db.init();
a = queue.add('shell', {'cmd': 'echo hello'})
b = queue.add('shell', {'cmd': 'echo world'}, depends_on=a)
print(a, b)"
uv run python -u -m fleet.worker worker-1 --budget-s 5
worker-1  task 1 (shell)  done
worker-1  task 2 (shell)  done
uv run python -c "from fleet import queue; print(queue.results([1, 2]))"
['hello', 'world']
uv run python -m fleet.dlq                          # dead-lettered tasks
uv run python -m fleet.dlq redrive <task_id>        # put one back, with what waits on it
uv run python -m fleet.conflicts                    # tasks waiting for a person
uv run python -m fleet.conflicts resolve <task_id> "keep the newer schema"
FLEET_WORK_MODULE=mypackage.mywork uv run python -u -m fleet.worker worker-1   # your own do_work(task)

Chapter 12

Syncing devices

Only the event ledger moves between machines. Each device writes its own events-<device>.jsonl in a sync folder that sits in a private git repo with a remote, and imports every device's file, skipping events it already has. Runs, steps, claims and the queue stay on the machine that owns them.

export ITERUM_SYNC_DIR=~/private-data/iterum      # the default; must be inside a git repo with a remote
uv run python -m fleet.sync sync      # export, commit, pull, push, import, rebuild knowledge
uv run python -m fleet.sync export    # only write this device's events
uv run python -m fleet.sync import    # only merge every device's events
Keep files from retired devices. They are the only shared copy of those events. Importing the same file twice changes nothing.
Chapter 13

Testing changes to Iterum

There is no unit test suite. Changes are checked with drills that crash the harness on purpose, and with recorded runs replayed through the real code. Run them against a scratch database.

CommandChecksTimeCost
fleet.merge_drillMerge gate refusals, the lock, a crash mid-mergesecondsfree
fleet.claims_drillClaim refusal, resume, renewal, takeover of a paused agentabout 50 sfree
fleet.kill_drillSIGKILL a worker mid-task and check recoveryabout 50 sfree
fleet.run (no plan)The six-step write-ahead drillabout 25 sfree
fleet.evalReplays every stored case; exit 1 if a regression case failssecondsfree
fleet.scorecard <before> [<after>]Eval cases at two git revisions; FIXED or BROKE per casesecondsfree
fleet.sweep a.json b.json --repeats 5Plans run N times in rotated order; pass rate beside costminutesbilled
 
export ITERUM_DB=/tmp/scratch.db ITERUM_DEVICE=test
uv run python -u -m fleet.merge_drill
uv run python -u -m fleet.claims_drill & uv run python -u -m fleet.kill_drill & wait
uv run python -m fleet.eval add resume-case <run_id>    # keep a real run as a regression case
uv run python -m fleet.scorecard main                   # did my working tree break any case?
When you add a check to a drill, break the code once to watch it fail, then undo the break by reversing your edit, not with git checkout, which also throws away uncommitted work.
